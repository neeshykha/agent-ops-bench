Agent Ops Bench — results

Does adding a second AI agent to support-ticket triage actually help? One generalist agent, two specialists, and a generalist plus a QA reviewer, run over the same 30 labeled tickets. Every number on this page is copied from the committed results/scorecard.md.

The QA reviewer paid for itself on the hard cases: 9 overrides on 30 tickets, 6 of which fixed a first-pass error and 2 of which broke a correct call — +4 net corrections at $0.60 each.

The reviewer added $0.080 per ticket. With it, severity accuracy rose from 70% to 80%, every labeled P1 was caught (7/7, versus 6/7 for the single agent), and the two "resolved lockout still classified urgent" tickets — the documented weak spot of the underlying classifier — were both corrected. The price is latency: the review is a second, sequential call, so time per ticket doubled (5.1s → 10.4s).

Single run per configuration on a deliberately hard 30-ticket subset. What that does and doesn't support is spelled out under How it was measured.

How it was measured

Workload

60 labeled synthetic support tickets for a multifamily IoT platform (smart locks, thermostats, leak sensors, access panels, a resident app), each with a severity label (P1–P4) and one of 7 routing teams, reused from claude-triage-simulator. The benchmark runs a 30-ticket subset weighted toward hard cases: all four "confusable pattern" groups (leak-sensor false alarms, already-resolved lockouts, multi-unit thermostat failures, understated property-manager tickets) plus a stratified sample of the rest. The subset holds 7 labeled-P1 tickets. Accuracy on it is deliberately lower than on the full set — the same generalist scores 75% severity / 87% routing on all 60.

Configurations

  • A · Generalist — one call with the full taxonomy (prompts/generalist.md).
  • B · Specialists — two parallel calls: a severity assessor that never sees the routing categories and a routing dispatcher that never sees the severity taxonomy (prompts/severity.md, prompts/routing.md).
  • C · Generalist + QA — the generalist call, then a reviewer that receives the ticket and the first-pass answer and may confirm or override, with instructions to override only for a rule-based reason (prompts/qa_reviewer.md).

Every call is claude -p … --model sonnet --output-format json through the Claude Code CLI. Each configuration was run once over the subset.

Metric definitions (as implemented in score.py)

Severity, Routing
Exact match between the prediction and the label.
P1 catch
Of the 7 tickets labeled P1, how many were predicted P1.
Under-triage
Tickets predicted less urgent than their label (e.g. labeled P2, predicted P3).
Cost/ticket
Sum of the CLI-reported total_cost_usd across all calls, divided by tickets. Measured from the CLI's JSON envelope, not estimated from token prices.
Avg latency
The CLI-reported wall-clock duration of each invocation. Config B takes the slower of its two parallel calls; config C adds its two sequential calls.
Override / catch / harm
An override is any ticket whose final severity or routing differs from the first pass. A catch is an override that took a ticket from not-fully-correct to fully correct (both fields); a harm is the reverse. An override that leaves a ticket wrong on either field counts as neither.
Cost per net correction
(Config C cost/ticket − config A cost/ticket) × 30 tickets ÷ (catches − harms).

What to keep in mind

  • One run per configuration, 30 tickets, no repeats — the differences are suggestive, not statistically tested. A one-ticket swing is 3.3 points of accuracy.
  • Config A and the first pass of config C are separate runs of the same prompt, so they do not agree ticket-for-ticket. The reviewer's catches and harms are scored against config C's own first pass; its added cost is config C minus config A.
  • The reviewer's prompt restates the generalist's taxonomy but adds one clause the generalist never saw: a lockout that is fully resolved with no ongoing gap is P3. Three of the nine overrides (T028, T029, T030) are the tickets that clause governs — two catches and one harm — so part of the reviewer's edge is a prompt difference, not independent auditing.
  • The CLI was invoked with its default tool set from the repository directory, and the harness does not record tool use, so nothing in the run rules out an agent reading the labeled dataset. There is no sign that it did.
  • The per-ticket raw outputs that produced these figures are gitignored; the committed scorecard is the only record of the run.
